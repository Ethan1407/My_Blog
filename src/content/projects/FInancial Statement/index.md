製作一套能自動診斷股票的系統，是我在接觸投資理財後一直想完成的目標。以下我將結合這段時間的心路歷程與五個開發階段的紀錄，詳細回顧這段將財報轉化為視覺化圖表的實作過程。

## 專案建置契機與前置準備
在我剛開始學習台股投資時，發現多數散戶（包括我自己）面臨著一個巨大的痛點：我們都知道基本面很重要，但企業財報裡的數據卻非常不容易讀。網路上的財經軟體雖然資料齊全，但對於新手來說資訊密度太高，缺乏直覺的總結。當時我心想：「如果能有一套系統，只要輸入股票代號，就能自動幫我算出各項指標，並用紅黃綠燈告訴我這家公司安不安全，那該有多好？」
起初，我對全端開發與 API 串接的邏輯並不熟悉，而且處理財報的 JSON 格式也讓我吃足苦頭。有了先前製作個人網頁與自動化工作流的經驗後，我深知先建立設計圖的重要性。在正式寫 Code 前，我花了幾天時間研究財經指標，結合大學課程所學，整理出「五大健康度架構」，並再次與 Claude 進行了深度的系統架構討論，確定了以 Python Flask 作為後端運算大腦、HTML/JS 作為前端視覺化的開發策略，這才讓我正式開始整個流程的設計。

## 1：API 串接與動態產業規則
第一個的目標是打通系統的資料來源——串接 FinMind 開放金融數據。我順利寫出了抓取損益表與資產負債表的程式，正當我以為一切順利時，系統卻在查詢「金融股」時發生了嚴重的崩潰。我跟 AI 來回修改了好久，才恍然大悟：原來金融業的財報結構和一般電子業完全不同，他們根本沒有「存貨」這種會計科目。為此，我再請 AI 修改底層邏輯，建立了一套「動態產業對照模組」，讓系統在運算前會先判斷產業別，自動套用或關閉特定規則。這個過程讓我深刻體會到，寫程式不只要懂代碼，更要懂這個領域的知識。

## 2：前端雷達圖與白話文生成
解決了後端數據後，接下來我將重心轉向了前端介面。我導入了 Chart.js 繪圖套件，將冰冷的數字轉化為直觀的「五大健康度雷達圖」。這個階段最考驗的是對齊與視覺舒適度，我不斷與 Claude 來回溝通，微調了深淺色主題（Dark/Light Mode）的配色。同時，我也實作了「AI 白話文總結」功能，為了避免 AI 產生幻覺（瞎掰投資建議），我嚴格設定了 Rule-based 的生成模板，讓所有的文字評語都是基於真實算出的財報指標來輸出，確保系統的專業度與嚴謹性。

## 3：ETF 分析與新聞走向探勘
為了讓系統更貼近現在大學生與存股族的真實需求，我決定加入兩個進階功能。第一是「ETF 成分股一鍵查詢」，讓使用者可以直接看到 ETF 底層的真實持股比例，甚至能在不跳轉頁面的情況下「預覽」成分股的財報。第二是利用 Google News RSS 串接即時新聞，並導入 NLP 自然語言處理技術。我親手建置了正負向情緒詞庫，讓系統能自動統計近期新聞的「利多與利空」，這兩個功能的整合，讓我的系統不再只是一個靜態的看盤軟體，而是一個動態的投資大腦。

## 4：效能撞牆期與雙層快取建置
接著，我邀請了幾位同學來幫忙進行封閉測試，結果發生了悲劇。當大家同時輸入代號查詢時，網頁陷入了無止盡的轉圈圈，接著跳出 429 Too Many Requests 錯誤。原來我們的查詢量把 FinMind API 的免費額度用完了。這個問題讓我知道一直用 API 來進行請遊也不是辦法，因此，我決定導入 Supabase 雲端資料庫，並結合伺服器端的記憶體快取來製作「雙層快取機制」。當有人查詢過某檔股票後，資料就會被存下來，下一個人查詢時只需幾毫秒就能回傳結果。看著終端機裡大幅減少的 API 呼叫次數，讓我莫名有一種成就感。

## 5：雲端部署與資安防護升級
最後，我將前端部署到 Vercel，後端部署到 Render。就像之前做個人網頁時遇到的「路徑問題」一樣，這次我也遇到了跨來源資源共用的阻礙，導致前後端無法溝通。不過有了之前的除錯經驗，我順利修改了路由與 Header 設定。而且為了保護辛苦建置的快取資料庫不被惡意串改，我還加上了 HMAC 的管理員金鑰驗證機制，為整個專案畫下一個安全且完美的句點。

## 結語
回頭看這段開發歷程，這不僅僅是一次專題實作，更像是一場橫跨金融與資訊的雙重挑戰。從一開始被 JSON 格式與會計科目搞得暈頭轉向，到後來成功導入 Supabase 快取並完成全端雲端部署，每一個 Bug 都逼著我跳出舒適圈，去學習全新的架構與思維。這個台股財報儀表板只是一個起點，它證明了透過自動化與 AI 工具的輔助，複雜的金融數據也能變得親民。
